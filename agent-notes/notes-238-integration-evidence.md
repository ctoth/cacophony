# Additional integration evidence, 2026-09-18

Read-only findings gathered while Fable reviews the original proposed revision:

1. `src/sound.ts:410-417` removes its pending playback-to-Sound play listener on every playback error. A new recoverable effect-build error during a pending mediaElement.play() must not suppress the eventual successful Sound play event. Preserve effect error cause/attachment data when Sound forwards it, and test media startup success after effect failure.
2. `src/sound.ts:269-276` starts inherited pitch-shift materialization outside `_preparePlayback` and catches/discards failure. A preparation guarantee cannot omit that task. Public pitch-factor reference/automation remains deferred, but inherited pitch build readiness/failure and cancellation must participate; separate internal ownership from general name lookup in `src/playback.ts:719-723`.
3. `Sound.preplay` commits shared holdings arrays. Concurrent asynchronous preparations cannot roll back by truncating to an old captured array length: one failed preparation could discard a later successful voice's bookkeeping. Remove only the failing preparation's own nodes/subscriptions/voice.
4. `Playback.play` recreates a buffer source on first start (`src/playback.ts:289-292`, `:503-529`), but retains the gain/effect/panner targets unless play options replace them. The preparation contract must state later play options are explicit overrides and panType changes invalidate prepared stereo-pan bindings. A guaranteed start helper that checks deadlines is extra scope; readiness alone does not prevent an application from waiting too long before starting.
5. `MediaStreamSound.preplay` and `PcmStreamSound.preplay` return an existing voice if one exists. Capture slots on actual voice construction, not every play/preplay call. Their synchronous materialization failure rollback is not the same as Sound/Synth; avoid describing universal existing rollback behavior.
6. Cross-owner shared native targets cannot promise isolated transactional initialization. Batch-initialization scope should be the new voice's exclusively owned parameters, with validation before writes and explicit unsupported results for external/shared initial targets. Ordinary explicit bindings may still disclose sharing and permit caller-directed native control under the documented tracking boundary.
